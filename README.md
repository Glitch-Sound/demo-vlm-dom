# demo-vlm-dom

ドラレコのような走行静止画に写る他車を、ローカルの VLM と DOM で解析して色付きの矩形で示すデモです。
注視優先度は画像で確認できる自車の前方進路との位置関係を表し、衝突リスクの予測には使用しません。

## 準備

Mac または Ubuntu、Python 3.13、`uv`、Ollama 0.35 以降を用意します。
Ollama サーバーを起動し、次のモデルをダウンロードしてください。

```bash
ollama pull qwen2.5vl:7b
ollama pull tev1
uv sync --locked
```

走行静止画を `data/src/` に置き、必要に応じて [setting.ini](config/setting.ini) を編集します。
入力ファイルは直下の名前順に処理します。

```bash
uv run --locked demo
```

結果は `data/dest/` に入力と同じファイル名・画像形式・画素寸法で保存します。
成功した画像の同名出力は上書きし、失敗した画像の出力は変更しません。
一枚が失敗しても次の画像へ進み、最後に成功・失敗件数、失敗したファイル名、処理時間を表示します。
車両が検出されない画像も、矩形なしで出力します。

## 判定と画像サイズ

他車が前方進路上なら「高」(赤)、進路の近くなら「中」(黄)、位置が分かりどちらにも該当しなければ「低」(青)です。
画像から位置関係を判断できない車両は「判定不能」として描画せず、理由と件数を表示します。
モデルの矩形が不正な場合はその車両を除外します。
VLM は自車線と各車両の位置関係・画像上の根拠を読み取り、DOM はその関係を使って判定します。
自車線や前方進路との位置関係が判別できない車両は判定不能にします。
画像上で小さく離れて見える車両は青枠とし、手前の車両は同じ車線なら赤枠、左右の車線なら黄枠で示します。

推論用画像は、設定した最大幅・最大高さに収まるよう縦横比を保って必要な場合だけ縮小します。
小さな画像は拡大しません。
VLM が返す推論用画像のピクセル座標を元画像へ換算し、元画像に描画します。

初回の画像解析前に VLM へ空の要求を送り、最初の車両判定前に DOM へ短い固定質問を送って応答を確認します。
固定質問の選択結果は車両の優先度には使いません。

## 設定

[setting.ini](config/setting.ini) の主な項目を示します。
タイムアウトは秒、画像寸法と線幅はピクセル、色は `#RRGGBB` 形式です。

| 項目 | 内容 | 既定値 |
| --- | --- | --- |
| `ollama_url` | Ollama の接続先 | `http://127.0.0.1:11434` |
| `preload_timeout_seconds` | 各モデルの初回ロード用タイムアウト | `600` |
| `inference_timeout_seconds` | 画像解析・車両判定用タイムアウト | `300` |
| `keep_alive` | モデルの保持時間 | `10m` |
| `inference_max_width` | 推論用画像の最大幅 | `1280` |
| `inference_max_height` | 推論用画像の最大高さ | `720` |
| `line_width` | 矩形の線幅 | `3` |
| `high_color` / `medium_color` / `low_color` | 高・中・低の枠色 | 赤 / 黄 / 青 |

設定が不正な場合は画像処理を始めず、項目名を表示します。
Ollama に接続できない場合やモデルが応答しない場合は、その画像を失敗として扱います。

## よく使う用語

| 用語 | 意味 |
| --- | --- |
| VLM | Vision Language Model。画像から他車、矩形、見える位置関係と根拠を抽出するモデル。ここでは `qwen2.5vl:7b` |
| DOM | Decision Only Model。VLM の説明から車両ごとの注視優先度を選ぶモデル。ここでは `tev1` |
| 注視優先度 | 静止画像で見える前方進路との位置関係による注視の順序。衝突可能性の予測値ではない |
| 自車線 | 画像下側の自車位置から前方に続く、画像上で確認できる走行車線 |
| 判定不能 | 前方進路との位置関係を画像から判断する根拠が足りない状態 |
| 推論用画像 | VLM に渡す、必要に応じて縮小した画像。出力画像は元画像の寸法を使う |
| OpenSpec change | 一回の変更を計画・実装・検証する成果物一式 |
| capability | 利用者に提供する、継続管理する能力の単位 |
| 能力別パッケージ | 一つの能力の CLI と処理をまとめる `src/app/<capability>/` |
| 共有契約 | 能力間で受け渡す型、保存形式、パスなどの取り決め |
| 受け入れ条件 | change が利用者の目的を満たすか判断する条件 |
| 証跡 | 検証の手順、環境、結果を後で確認できる記録 |

要件の正本は [OpenSpec 仕様](openspec/specs/driving-scene-annotation/spec.md)、受け入れ条件は [アーカイブ済みの change](openspec/changes/archive/2026-10-19-demo-vlm-dom/proposal.md) に記載しています。
能力と実装パッケージの対応、共有契約、依存方向は [設計](openspec/changes/archive/2026-10-19-demo-vlm-dom/design.md) に記載しています。

## 開発

開発環境では Node.js と npm も用意します。
必要な依存関係を同期し、品質検査を実行します。

```bash
uv sync --locked
npm ci
uv run --locked pytest
uv run --locked pre-commit run --all-files
npm run check
```

Python コードは `src/app/driving_scene_annotation/`、自動テストは `tests/` に置きます。
機能変更は OpenSpec change の成果物を更新してから実装します。
README などの日本語の案内文では、文末の句点の直後で原則改行し、同じ段落を続ける場合は `。<br />` の後で改行します。
括弧は半角の `(` と `)` を使います。
